# 首版范围与验收基线

版本：v0.1 · 2026-10-30 · Asia/Shanghai。

本文区分用户确认的业务要求、实现建议和待决事项。用户已授权开始设计开发，并要求先保存里程碑与持续开发记录；这不代表下面待决项已经获得确认。

## 用户确认的要求

| ID | 要求 | 首版验收 |
|---|---|---|
| R-01 | 以 Twenty 为内部业务工作台，承载客户从企业注册到支付网关申请的全过程 | 员工可从同一客户档案进入资料、企业办理、网关申请、材料及邮件 |
| R-02 | 可以访问外网 | OCR、邮件、模型和必要外部 API 可按配置连接；不再以完全离线为前提 |
| R-03 | 不做 Hostinger | 首版无 Hostinger 账号、主机、采购、部署、开邮箱或建站功能 |
| R-04 | 客户设负责人后，其他员工可查看，只有负责人可修改和办理 | 有功能权限的员工可读；每项业务写操作同时检查当前客户负责人 |
| R-05 | 管理员可查看、处理全部客户并修改负责人 | 管理员改派有审计；非管理员不能自行改派或改请求参数越权 |
| R-06 | 邮箱 AI 回复与翻译必须迁移 | 来信翻译、回复方向、中文意图起草英文、回译、编辑及人工确认发送可用 |
| R-07 | 暂不迁移企业自动申请、指纹浏览器等桌面端功能 | 首版企业办理采用人工记录/推进；不依赖本地桌面程序或自动浏览器 |
| R-08 | 驾照录入必须支持批量 | 单张/多张上传、逐项识别核对、重复处理、批量提交、部分失败重试 |
| R-09 | 建立里程碑文档及专门目录持续记录开发过程和变动 | 本目录的计划、进度、决策、变更与日志同步维护 |
| R-10 | 用户亲自测试每个里程碑 | 开发和自动验证通过后交付测试入口、合成账号及验收清单，等待用户反馈后进入下一里程碑 |

“可查看”受模块/功能查看权限约束，不等于开放系统凭据或不相关的管理设置。“负责人可以办理”也不替代邮件发送等具体功能权限。客户负责人是新要求，不能拿旧系统的 `createdBy` 或申请负责人直接冒充。

## 延续的产品边界

- 员工和管理员使用；客户门户与客户登录不在首版。
- 网站由其他服务建设；这里只登记申请所需域名、网址和邮箱资料。
- 企业设立记录、EIN 记录与网关申请分别建模，支持人工推进和证据关联。
- 客户办理阶段、客户完成、企业申请状态和网关申请状态分别表达。
- 单在办、不可变申请定稿、补件证据、结果纠正和操作归因作为迁移兼容规则保留。
- 草稿材料与正式材料分开；草稿不进入申请定稿。
- 卡头查询、账单模板作为 Web 工具迁移；内部 IM 历史采取归档优先，完整聊天重建另作范围决策。
- 已退役的 Grist 集成、PDF 转 HTML 不恢复。

## 技术建议（不是额外的用户承诺）

1. Twenty 展示通用列表、关联与协作入口；专用业务服务执行办理命令及材料处理。
2. 普通员工通过 Twenty 原生接口只读业务对象，负责人在自定义业务表单/按钮中办理，由后端校验身份与负责人。此方案不依赖购买动态行级权限；具体集成须通过 M0 验证。
3. 纯翻译与业务推进分开，避免非负责人点击翻译后改变申请状态。AI 草稿、补件处理、发送和状态更新仍受办理权限约束。
4. 新建客户默认由提交建档的员工负责、管理员可指定负责人，是候选规则，尚未最终确认。
5. 延续已验证的原引擎规则、契约和测试，逐步适配，避免迁移同时重写全部业务。

## 首版功能清单

| 模块 | 纳入 | 暂不纳入 |
|---|---|---|
| 建档 | 驾照多选/拖拽、OCR、核对、重试、查重、批量提交、负责人衔接 | PDF 驾照、一图多人拆分、自动免确认入库 |
| 客户 | 个人、企业、银行业务资料、材料、历史、负责人、归档 | 自动跨档案合并自然人、客户门户 |
| 企业办理 | 设立订单、人工状态、州审批结果、EIN、文件 | RPA、自动付款、IRS 自动操作、桌面领单 |
| 网关申请 | 开始申请、定稿、平台、状态、补件、负责人约束、完成与纠正 | 自动向支付平台提交、测试付款 |
| 邮箱 | IMAP/SMTP、会话归属、翻译、回复建议、AI 草稿、回译、人工发送 | 默认 AI 自主发送、AI 自动读取附件、任意目标语言扩展 |
| 工具 | 卡头目录查询、账单编辑和独立渲染服务入口 | Hostinger、建站、指纹浏览器、代理/设备执行 |
| 协作 | 业务待办、通知、操作记录 | 重建完整内部聊天产品 |

## 必须在对应开发任务前解决的待决事项

| ID | 问题 | 当前建议 | 最晚决策点 |
|---|---|---|---|
| Q-01 | 新建客户默认负责人；无负责人客户谁能办理；历史客户如何分配 | 新建默认提交者；管理员可指定；历史待分配客户先由管理员处理 | M1 建档写入与历史试迁前 |
| Q-02 | 旧申请负责人与新客户负责人不一致时如何处理 | 客户负责人决定当前权限；保留历史提交/确认人，不靠旧申请负责人放权 | M2 申请迁移前 |
| Q-03 | 邮件有证据时自动改变申请结果的现行行为是否保留 | 首先分离纯翻译；系统自动推进需独立授权策略与审计 | M3 自动推进接入前 |
| Q-04 | 内部聊天是否重建；哪些历史消息需迁入 | 保留旧系统只读历史；首版优先业务通知与记录 | M4 范围冻结前 |
| Q-05 | 账单渲染服务的可用部署和数据生命周期 | 验证现有渲染服务再决定直接接入或修复 | M4 工具验收前 |

这些问题不阻止文档建立和 M0 的合成样本验证。验证样本使用明确分配负责人的客户，不将临时测试策略当作正式默认规则。

## 首版通过条件

- 一批合成驾照可建立多个客户，失败项独立处理，同一建档项重放不重复创建。
- 两名员工 A/B 和管理员可验证“都能看、只有对应负责人能办、管理员可改派”。
- 转交后，旧负责人已打开的页面及尚未执行的业务任务不能继续修改或发信。
- 一位合成客户可完成企业人工办理、EIN 记录、网关申请、补件、获批与纠正。
- 邮件原文、译文、AI 回复、回译、附件及确认发送链路完整，重复发送被防止。
- 原生 API、导入、工作流、AI/MCP 等入口不能绕开办理权限。
- 数据迁移对账及回退演练完成，旧系统不会继续对同一批客户业务双写。
