## 1. 已确认范围与未决项

### 1.1 已确认范围及据此制定的设计规则

批量驾照录入、邮箱 AI 回复与翻译、负责人可写/其他员工可看、管理员改派及暂缓桌面能力，是用户明确要求。逐项核对、纯翻译拆分、回复辅助写授权和防止关联绕过权限，是本版继承旧实现或由上述要求推导的设计规则，不另行声称用户逐项指定了实现细节。

1. 首版必须支持驾照录入，且可以批量上传、逐项核对和批量提交。
2. 首版必须包含邮箱 AI 翻译、AI 回复及人工确认发送。
3. 员工可按功能权限查看客户。对于已有负责人的客户，只有客户负责人或管理员可以修改资料和办理业务；管理员可以处理全部客户并改派负责人。
4. 客户负责人不是原系统的申请负责人。两者分别记录，不能把申请负责人、客户创建人、字段确认人直接当成客户负责人。
5. 有查看权限的员工可以使用纯翻译。纯翻译不能同时更改申请状态、写入补件、发送邮件或改派负责人。
6. AI 草稿、发信、补件及申请状态写入属于办理动作，受客户负责人或管理员授权约束。
7. 关联已有客户、向其添加附件或采用识别字段，必须取得目标客户负责人或管理员的操作授权；不得通过另建客户绕过已有客户的负责人限制。
8. 企业自动申请、指纹浏览器、代理、设备执行等桌面能力延后；首版只保留企业人工办理记录。浏览器选文件即可完成首版建档。
9. 不迁移 Hostinger 或建站平台。网站与域名可作为办理资料引用，邮箱可接独立服务商。

### 1.2 技术建议，尚未作为用户决定

- 新客户首次建档时默认由本次提交者负责；管理员可在提交时指定负责人。此方案尚未确认，不能在实现中悄悄采用，也不能把 `createdBy` 自动解释为负责人。
- 建档未提交区由批次创建人或管理员维护，其他员工按功能权限查看。这是候选协作规则；客户尚未创建时如何授权必须在实施前明确。
- 将现有邮件的“读懂”拆成纯阅读辅助、办理建议、经授权的业务执行三个服务边界；实际 API 命名和存储方式待集成设计确定。

### 1.3 实施前必须决定

| 编号 | 未决项 | 影响 |
|---|---|---|
| OM-01（Q-01） | 首次创建客户的负责人默认值、管理员指定方式、无负责人旧客户如何接管 | 新建事务、迁移回填、首次可办理人 |
| OM-02（Q-03） | 来信解析后何时允许自动更新申请、谁能授权、授权范围及撤销条件 | 自动状态更新、补件写入、后台执行身份 |
| OM-03 | 未归属客户的邮箱/来信由谁办理，如何分配与确认归属 | 未分配收件箱、发信、草稿、历史补审 |
| OM-04 | 批次创建后、客户创建前的编辑及提交协作权限 | 建档暂存区、交接、他人提交 |
| OM-05 | 疑似重复但确属不同人的复核与批准方式 | 防止误合并，同时防止通过另建绕过负责人限制 |
| OM-06 | 来信“仅翻译”和摘要/要求提取的首版按钮组织 | 保持纯阅读操作无业务写副作用 |

OM-02 未确定前，不能以“沿用原系统”为由默认开启自动推进，也不能暗中宣布已改为全人工。必须先写清策略和验收，再启用相关办理执行路径。已确认的纯翻译与人工发信可以独立设计、实现和验证。

OM-03～OM-06 是对应阶段的设计细项，由实施者在 M1/M3 执行计划中提出具体选择并记入决策；涉及新增人员权限或改变已确认业务规则时再由用户决定。它们不阻止 M0，也不要求用户现在逐一选择界面细节。

## 2. 共用权限与数据边界

### 2.1 功能权限和客户办理权限同时成立

后端每次动作需结合当前会话身份、功能权限、目标客户归属与当前负责人作判断。前端按钮隐藏只是反馈，不是授权。

| 动作 | 员工有相应功能权限 | 还须客户负责人或管理员 |
|---|---|---|
| 查看客户、驾照附件、重复线索、邮件、译文 | 是 | 否 |
| 对可读邮件运行纯翻译 | 是 | 否 |
| 上传至未提交建档批次、核对、重新识别 | 是 | 未创建客户前遵循 OM-04，不虚构客户负责人 |
| 关联已有客户、采用字段、向已有客户附加资料 | 是 | 是，以目标客户为准 |
| 新建客户并确认提交 | 是 | 遵循 OM-01；提交时必须确定合法负责人分配结果 |
| 生成回复方向、AI 草稿、重新起草 | 是 | 是，以实际邮件业务归属为准 |
| 人工发送回复、处理补件、改申请状态 | 是 | 是 |
| 改派客户负责人 | 管理员操作能力 | 仅管理员 |

查看和翻译权限不意味着允许把译文结果用于执行办理动作。纯翻译可以写入自己的任务状态、用量和翻译缓存，但不能借用这次请求调用状态推进、补件创建、发信或负责人变更。

### 2.2 归属解析和并发

- 邮件已关联申请时，以该申请的客户为业务归属；未关联申请时，才回退到邮箱的客户。邮箱后来改绑不能改变旧申请邮件的业务归属。
- 不能信任客户端传入的 `customerId`、`ownerId` 或 `userId`；必须从申请、会话、邮箱、附件等实体关系重新解析。
- 管理员改派后，旧负责人不得继续通过已打开的页面、缓存权限、旧草稿或旧队列执行新的业务写入。重要动作在最终提交前重新读取归属及负责人版本。
- 已被 SMTP 接受的发送不能因事后改派而“撤回”；审计保留执行时合法操作者和执行结果。改派与发送的并发窗口需有服务端测试。
- 业务数据仍可供有权限员工查看。无需把所有客户列表、搜索和计数改成“仅本人客户可见”；“我负责”是便利筛选，办理权限另行校验。
- 负责人修改记录、原建档人、OCR 发起人、核对人、提交人、字段操作人分别保留，不能相互覆盖。

## 3. 批量驾照建档

### 3.1 迁移兼容基线

| 项目 | 参考实现 | 首版要求 |
|---|---|---|
| 格式 | JPG/JPEG、PNG、WEBP、HEIC | 保留上述格式的产品范围；服务端按内容验证，不能只认扩展名 |
| 文件大小 | 每文件不超过 20 MB | 作为兼容基线；实际代理层、服务层和模型可用性在 M0 验证 |
| 单次上传 | 最多 30 张，可追加到已有批次 | 上传前说明限制；超限有明确提示，不静默丢文件 |
| 单次提交 | 最多 100 个条目 | 大批次的分段提交方式待设计；不得以 UI 一次选择掩盖接口限制 |
| OCR 并发 | 默认最多同时 3 张 | 作为迁移基线，不等于已验证分布式全局并发或吞吐保证 |
| 输入单位 | 一张图片对应一个人的一张驾照正面 | 不承诺 PDF、多页 PDF、一图多人拆分、正反面联合识别 |
| 字段 | 名、姓、生日、驾照号、签发/到期日期、驾照地址 | 沿用字段语义和格式规范；不将 middle name 自动并入姓名 |

HEIC 的接受、解码和模型支持需要分别验证。模型识别能力和上传成功是两个结果，不能把“已接受文件”显示成“已识别成功”。批量业务不依赖文件夹读取、Electron 或其他桌面能力。

### 3.2 用户流程

1. **上传。** 员工选择或拖入多个文件，系统建立批次和独立条目；展示文件名、接受/拒绝原因、当前进度。可向同批次追加文件。
2. **逐项识别。** 每张独立排队，展示识别中、已识别或识别失败。识别值只是候选，不能直接写客户资料。
3. **逐项核对。** 同屏显示原图、候选字段和不确定标记；人工修正并确认当前项。识别失败时可重新识别，也可对照已上传原图人工转录。
4. **处理重复。** 显示同图、同驾照号、同名同生日、同名等线索；员工核实后选择允许的处理方式。若目标客户由别人负责，可查看差异，但不能采用字段、添加附件或办理关联。
5. **批量提交已确认项。** 只提交已核对且处理决定明确的条目；逐项返回结果。任何失败不得撤销已经成功提交的其他项。
6. **查看结果。** 分组显示已创建、已关联、失败、待处理、已跳过；支持进入客户和单项重试。网络中断后先读取结果，不把“请求未返回”解释成“全部失败”。

不能把“批量”实现为默认认可全部 OCR 结果。一键提交的对象是已逐项确认的条目，而非全部上传文件。

### 3.3 状态与记录

迁移需保留条目级 `uploaded / recognizing / recognized / recognition_failed / confirmed / submitting / done / failed / skipped` 的状态语义；具体实现可简化中间状态，但不能丢失“识别失败”和“创建失败”的区别。

每项至少能追溯：批次与条目 ID、文件引用和内容指纹、原文件名、候选值、不确定字段、识别模型、识别错误、人工确认值、录入方式、重复线索、处理决定、结果客户、上传/OCR/确认/提交操作人及时间、并发版本。

识别为反面或非驾照时明确提示。不能仅因模型给出了部分字段就将该图静默当作有效驾照正面；改传正面或异常转人工的具体放行条件纳入验证。对于一图多证或多人合照，应明确当前不支持，不猜测其中哪一人为客户。

### 3.4 查重、权限与提交事务

- 重复提示只是核实线索，不能自动合并客户，也不能默认覆盖旧资料。
- 提交前再次查重，覆盖同批次较早成功项及其他员工在核对后新增的记录。
- “仅关联”不改变旧字段和旧图；“关联并核对差异”只采用明确勾选的字段。两类关联都必须检查目标客户负责人授权。
- 差异核对后，旧字段若被他人修改，返回需重新核对，不能以最后写入覆盖。
- 已确认是同一客户且该客户有其他负责人时，不得通过“仍要新建”规避限制。确属不同人的同名/相似证件处理走 OM-05，不默认拥有任意另建权限。
- 每项提交独立事务：新客户、个人档案、驾照正面附件、负责人分配结果、操作归因、条目结果必须一致成功。客户记录创建成功但附件未关联，不能显示“已创建”。
- 已成功的条目重复提交返回原客户和原结果；已有失败结果可在修正原因后重试。基于条目 ID 的提交幂等不能替代上传请求幂等。
- 原上传接口没有与条目提交相同的请求幂等保证。迁移实现应设计稳定上传请求/条目标识或核验恢复方式，避免超时重试产生无法辨认的重复待处理项；采用哪种方式待技术设计确定。
- 保存、确认与决定采用并发版本；批量结果逐项带错误码和可执行下一步，不只返回一个总失败。

### 3.5 异常反馈

| 场景 | 必须表现 |
|---|---|
| 格式不支持、空文件、超限、文件内容损坏 | 指出具体文件和原因；有效文件的处理结果仍可见 |
| 模型不可用、超时、无法识别 | 该项标失败；可重试或对照原图转录，不阻塞其他项 |
| 反面、非驾照、多人/多证无法确定 | 提示换正确图片或人工核实；不制造确定字段 |
| 字段缺失/格式错误 | 定位对应字段；未确认不能提交 |
| 新发现重复 | 返回条目核对区重新作决定；其他成功项不回滚 |
| 目标负责人改变或无办理权 | 拒绝业务写入，保留核对结果供交接；不自动另建 |
| 提交响应丢失 | 读取批次结果后重试同项；不得重复生成客户 |
| 服务重启 | 识别任务可恢复；已完成项不重复送模型或重复建档 |

## 4. 邮箱 AI 翻译、回复与发送

### 4.1 已实现能力与首版承诺

| 能力 | 参考实现范围 | 首版迁移边界 |
|---|---|---|
| 来信翻译 | 英文邮件纯文本转中文，最多输入 12,000 字符；与摘要/要求/状态判断同一次“读懂”执行 | 必须有无业务写副作用的纯翻译；原文和译文可对照；长文本处理方式需明确 |
| 回复方向 | 公司/平台/申请状态背景 + 最近 3 封往来 + 当前邮件，生成中文方向 | 保留基于邮件的建议，作为办理动作检查负责人 |
| AI 草稿 | 中文意图 + 当前原信最多 10,000 字符 + 公司/联系人/邮箱/申请编号 → 英文纯文本 | 首版必须保留；生成前展示实际上下文范围，不承诺完整会话记忆 |
| 中文回译 | 英文草稿逐句回译为中文 | 保留；人工改英文后标明回译已不对应当前文本 |
| 防编造提示 | 提示原信、事实、意图中未找到的数字、日期、金额 | 保留辅助提示，不宣称可检出所有事实错误 |
| 人工编辑 | 可改收件人、抄送、主题、英文正文 | 保留；生成不等于发送 |
| 重新起草 | 重新用 `messageId + intent` 起草 | 保留现有语义；不承诺对当前人工编辑稿 AI 改写 |
| 附件 | 选择实际所属客户当前附件，合计最多 20 MB | 保留；发送时重新校验；不把草稿箱文件自动变成有效申请定稿 |
| 人工发送 | 二次确认、会话变化提示、幂等、防不明结果重发 | 首版必须完整迁移 |

不作为首版迁移承诺：任意目标语言选择、附件内容自动理解/翻译、对人工编辑稿 AI 改写、编辑后的自动重新回译、任意新上传附件的 AI 处理、AI 自动发送。需要这些能力时另立需求，不以“大模型理论上能做”标为已有。

### 4.2 纯翻译与办理解析分开

**纯翻译入口**面向有查看权限的员工。校验可读性和 AI 使用能力后，读取原文、调用翻译模型、保存译文或翻译任务结果并返回。禁止在这条调用链中更改分类、关联申请、创建补件、更新状态、发送邮件或更新客户完成。

**办理解析入口**可以产生分类、对方要求、明确期限、状态建议及原文证据。能否自动执行这些建议遵循 OM-02；用户界面必须区分“AI 建议”和“已执行的业务变更”。只有拥有目标客户办理权限的人员或明确授权的系统服务，才能触发实际业务写入。

旧系统事实：现有“读懂”会在已确认归属申请时直接推进状态，包括获批/拒绝；没有确认归属时不给状态清单，状态应为空；补件只接受能在原文找到的引用。迁移可以复用校验逻辑，但不能直接复用带副作用的整个入口作为纯翻译。

### 4.3 回复交互

1. 阅读原文，可展开中文译文；翻译失败不影响查看原信。
2. 有办理权限者打开回复面板，看到发件邮箱、被回复邮件、业务客户和关联申请。默认收件人来自该邮件，但允许人工更改。
3. 输入中文意图，或选择 AI 回复方向。生成前重新检查当前负责人，不能仅依赖进入页面时的权限。
4. 生成英文草稿与中文回译，显示防编造提示。正文、收件人、抄送、主题均可编辑；重新生成可能替换当前正文，交互需明确防止误覆盖人工修改。
5. 按需从目标客户当前附件勾选文件，显示文件名和总大小。附件内容默认不送模型；AI 不能仅因正文提到“已附上”就自动选择文件。
6. “提交发送”打开确认页，逐项展示发件邮箱、收件人、抄送、主题、完整正文、附件及归属申请。
7. 员工最终确认后才调用发送。会话新增来信或他人回复时要求查看变化并再次明确确认，不能静默发送旧上下文的草稿。
8. 结果区分 SMTP 已接受、确定未发送、结果不明、已发送副本保存失败。发送后业务状态如何变化亦须经过独立授权路径。

草稿属于生成者和原邮件。不得由其他员工提交一份不属于自己的草稿；管理员代办是否采用复制为新草稿等方式须在实现中明确，不能绕过审计归因。客户转交后的历史草稿可保留查看，但原负责人失去办理权后不能继续用它发送。

### 4.4 上下文、模型与数据最小化

- 参考实现回复方向使用最近 3 封历史，每封最多 2,500 字符，当前邮件最多 8,000 字符；真正生成草稿仅使用当前邮件最多 10,000 字符、四项业务事实和员工意图。两者上下文范围不同，不能声称草稿已理解完整往来。
- 来信翻译参考输入最多 12,000 字符。首版须选择分段翻译或显式提示截断，不能把部分翻译呈现为全文完成；具体策略列入 M0/接口设计验证。
- `mail_read` 与 `mail_draft` 独立指定服务商和模型；回译走 `mail_read`，回复方向和正文走 `mail_draft`。保留 OpenAI/Anthropic 协议兼容配置能力，实际模型可用性需验证。
- 模型未配置、不支持协议、预算耗尽、结构化输出校验失败均给出可理解错误，不悄悄换为未授权服务商。
- 邮件 AI 外发正文的同意、配置版本和批准流程属于现行产品能力，需要迁移设计明确如何承接；本文不代替配置批准，也不要求每次正常翻译重复向用户征求许可。
- 凭据只在服务端获取，不进入 AI 上下文、应用日志、确认页面或迁移文档。客户资料和邮件正文不写入开发记录。
- 原系统会在读懂时引用同发件方历史样例和经验。纯翻译无需继承整套学习上下文；办理解析复用时须确认样例范围与用途，不自动扩大模型可访问资料范围。

### 4.5 发信事务、幂等与异常

- 草稿/发送接口分别校验 AI 办理能力和发信能力，并叠加客户负责人或管理员检查。管理员全客户可办理不代表可以跳过身份及功能授权。
- 同一发送意图使用稳定幂等键。服务端同时核对操作者、原邮件、草稿和键的绑定；同键重放不得再次连接 SMTP 发送。
- 先保存 `sending` 记录再调用 SMTP，最终记录 `sent / failed / unknown`。进程中断必须留下可核验任务，不能简单当成失败重发。
- 只有明确未发出的失败才可重试；已提交后结果未知必须先核验。不能自动重试可能已被接收的邮件。
- 附件必须属于实际邮件客户、仍是当前有效附件且在大小限制内；文件被移除、替换、归属变化或负责人变化时停止发送并要求重新核对。
- 会话版本冲突要求人工复核；“仍要发送”不能绕过负责人、草稿归属、附件及幂等校验。
- SMTP 接受不等于对方送达。已发送副本失败不能把已成功发送降成“可重新发送”。
- 发送成功但后续业务状态写回失败，需要独立记录并可恢复；不得重发邮件来补偿状态写回失败。
- 确认后但外部调用前发生改派的授权边界需要设计并发控制与审计；不以旧页面权限长期授权外部操作。

### 4.6 后台执行边界

同步、新来信翻译、归属后重读、恢复任务、历史补审、补件及状态推进应明确分开。

- 自动同步和纯翻译可采用经过配置授权的系统身份，不因用户退出登录失效；不能借系统身份无限执行办理写入。
- 用户发起的办理任务应记录发起人、目标客户、负责人/授权版本和任务类型；执行及最终写回时重新检查适用授权。
- 系统自动办理策略未决定前，不启用隐含的所有客户自动状态写入。OM-02 应定义服务身份、授权范围、人工覆盖优先级、撤销及恢复规则。
- 队列和重启恢复不能绕过客户转交、客户删除冻结、申请结束、归属变化及 AI 配置关闭。
- 历史补审应预览范围和数量，按时间顺序执行；重放不得重复产生补件或状态变更。
- 业务更新必须经过统一领域命令，同步重算客户完成并保留来源/原文证据；不能由邮件工作进程直接随意改 Twenty 字段。

- [ ] 模型未配置、AI 关闭、配置未批准、输出无效、长邮件及任务恢复有明确反馈，不静默改变服务商或扩大权限。
