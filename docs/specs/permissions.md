# 客户负责人权限规格

状态：设计规格，尚未实现或完成端到端验收。
更新日期：2026-10-31（Asia/Shanghai）。
适用范围：company-helper CRM 首版业务扩展。

## 1. 已确认的业务规则

本节为用户已确认要求；后文的新建、未分配客户规则另标为提案。

| 操作 | 普通员工 | 管理员 |
| --- | --- | --- |
| 查看客户资料及业务记录 | 在具备对应功能读取权限时，可以查看其他员工负责的客户 | 在具备对应功能权限时，可以查看全部客户 |
| 修改资料、办理业务 | 同时具备对应功能权限，且是该客户的当前负责人 | 在具备对应功能权限时，可以处理全部客户 |
| 更改客户负责人 | 不允许，包括将客户转给自己 | 允许 |
| 修改历史操作人 | 不允许 | 不因转交而修改历史操作人 |

负责人限制是业务操作授权，不能代替现有功能权限。拥有客户不等于拥有发信、AI、材料管理等全部功能；管理员资格也不能由客户端声明。

授权逻辑为：

```text
可读 = 身份有效 && 工作区成员有效 && 具有对应功能读取权限
可办理 = 身份有效 && 工作区成员有效 && 具有对应功能操作权限
         &&（当前客户负责人 == 当前用户 || 当前用户是业务管理员）
可改派 = 身份有效 && 工作区成员有效 && 具有负责人分配权限
         && 当前用户是业务管理员
```

“办理”包括新增或修改申请、推进状态、提交补件、增删改客户材料、完成客户任务、修改业务备注、发送邮件，以及触发具有这些效果的自动化。纯读取和纯翻译不属于业务办理。

## 2. 技术方案及原生功能边界

采用 **Twenty 原生只读业务工作台 + 自定义业务表单 + 业务后端授权写入**。

普通员工可使用原生列表、详情、搜索及获准的 REST、GraphQL、MCP 读取。所有受客户负责人约束的业务对象，对普通员工禁止原生新增、修改、软删除、恢复及永久删除；负责人字段也不能例外开放。原生表格直接编辑自己的客户同样被禁止，编辑和办理须进入自定义业务表单。

后端验证用户身份、功能权限、当前负责人及业务状态后，用服务专用身份写入 Twenty 或业务存储。管理员可通过管理功能处理全部客户并改派；业务状态转换仍须遵守相应业务规则。

本方案使用静态对象、字段及动作权限，负责人条件由独立业务后端实现，**不是免费版原生动态 RLS**。源码具备某项能力不代表部署中已配置或验收。首次实施须核对实际 Twenty 版本、对象权限、动作权限及已有共享授权。

### 2.1 普通员工的原生权限

- 对客户、企业办理资料、申请、交付步骤、客户任务、业务备注、材料及其他受控业务对象允许必要读取，禁止全部业务写入。
- 对关联、中间对象也采用同样限制，防止通过更改关联把别人的申请、材料或邮件挂到自己名下。
- 不授予可以改变授权规则的数据模型、角色、应用管理等控制面权限，不提供可自行取得高权限凭据的路径。
- 原生发信、导入、可写业务的工作流、AI 工具及 MCP 写动作须禁止，或仅对受控管理员/服务身份开放。对象只读并不能自动禁止独立的发信等副作用。
- 排除可以向员工扩写的记录共享授权。不得给普通员工受控业务记录的 `READ_WRITE`、`FULL` 或其他等效写授权；不能仅检查对象角色而忽略已有共享记录。
- 若标准 Task、Note 等对象还承担不受客户负责人约束的个人功能，应采用独立的客户业务对象或明确的后端接口。不能为了个人任务编辑而开放全部客户任务的原生写入。

配置变更、升级或安装应用后，要重新检查上述入口，防止新增的写工具或共享授权突破只读边界。

### 2.2 服务身份与用户身份

服务专用写入 key 只保存于后端，不下发到浏览器、自定义前端组件、员工 MCP 配置或客户端日志。它表示集成服务，不能充当发起操作的员工身份。

业务后端须使用可信的登录/授权流程确认用户。例如，可由服务端使用调用者的用户会话或带用户的授权访问 Twenty 受保护的 `currentUser` 查询，再映射稳定的用户 ID 和工作区 ID。具体会话交换、续期及失效机制需在接口实现时验证；不能只解码未经验证的 JWT，也不能相信前端传来的 `userId`、`isAdmin` 或角色名。

身份映射以稳定 ID 为准，不仅按可修改的姓名、邮箱匹配。每次业务命令检查当前成员状态及功能权限；管理员资格来自服务端可信配置或权限查询。

接口使用明确业务命令，例如“更新客户资料”“提交补件”“发送回复”“改派负责人”，不暴露使用后台 key 的任意对象、任意字段 CRUD 代理。普通更新接口必须拒绝负责人及其他只允许专门命令修改的字段，防止批量赋值绕过授权。

## 3. 客户归属与共享数据

每项业务写入都必须解析出唯一、可信的客户归属。概念字段名如下，实际 Twenty 对象及字段名称由数据模型规格确定：

| 数据 | 权限归属来源 |
| --- | --- |
| 客户主记录 | 当前记录的客户 ID |
| 企业资料、申请、交付步骤、客户任务 | 已保存的客户关系，或由服务端沿已保存关联解析 |
| 材料、附件及上传任务 | 服务端保存的客户/申请归属；最终挂接时再次检查 |
| 邮件会话、草稿、发送任务 | 已确认的业务归属；关联申请时使用申请所属客户 |
| 批量操作 | 对每个目标分别解析客户和授权，不以首条记录代表整批 |

客户端提供的 `customerId` 只能用于请求定位，不能覆盖已有业务归属或成为授权事实。修改申请所属客户、邮箱绑定、任务关联、附件挂接等跨客户关系，应走专用命令，校验源、目标以及所有受影响记录；不得通过搬移关联绕过原客户权限。

归属缺失、冲突或存在多个不同客户时，普通业务写默认拒绝并要求先消除歧义，不回退为“任何员工可操作”。修复归属也须通过受控管理操作并留痕。

### 3.1 共用 Person/联系人

同一个 Person 可能关联多个客户。员工负责其中一个客户，不代表可以修改会影响其他客户的共享联系人主记录。

首版技术方案为：共享身份主档由管理员维护，客户特有的联系人信息、沟通偏好及业务资料保存为客户范围的记录，由该客户负责人维护。若后续允许员工修改共享主档，必须定义并校验所有受影响客户的授权，不能只检查请求中提供的一个客户 ID。

## 4. 负责人、改派与并发

客户需持久化当前负责人标识及递增的 `ownerVersion`。负责人变更不修改历史 `actorId`、`createdBy`、发送人、审核人或已完成动作的发起身份。

管理员改派须通过专用命令，记录客户、原负责人、新负责人、管理员、时间、原因及前后 `ownerVersion`。普通员工不能通过原生字段、业务更新接口、关联修改或异步任务改派。

### 4.1 同步操作

后端在实际提交业务写入的事务内检查最新负责人及版本，避免“页面打开时有权限、提交时已转交”的情况。涉及多个业务表时，相关业务变更必须具有一致的授权边界。

若授权事实与 Twenty 投影不在同一数据库，须选定一个权威的负责人存储，业务授权读取该权威来源；同步延迟不能恢复旧负责人权限。Twenty 负责人字段作为投影时，也不得由旁路修改。具体存储及同步方案属于实施待验证项。

### 4.2 异步任务和不可逆动作

具有业务副作用的任务至少保存：发起用户 ID、工作区、客户 ID、动作类型、发起时 `ownerVersion`、幂等键及必要的业务版本。

- 排队时检查权限，执行前再次检查当前身份、功能权限、负责人及 `ownerVersion`。
- 负责人版本变化后，旧任务不得自动冒用新负责人继续执行。未发出的邮件、未提交的申请、未写入的补件等应进入明确的阻止/待重新授权状态。
- 即使原任务由管理员发起，也应识别过期的负责人/业务版本，避免基于旧交付上下文静默执行；管理员可核查后重新发起。
- 发信等外部副作用与改派须使用共同的客户级调度锁或等效排他机制。不能仅在外部请求前读一次负责人，然后允许改派并发穿过检查与发送之间的空隙。
- 已经向外部系统发起的动作不能视为可撤销。改派流程应识别正在执行的动作，等待其完成或明确标记结果不明后协调处理；不得把已发生的发送改写为新负责人发起。
- 结果不明的发送不得因为重试、改派或页面刷新直接再次发送。幂等与结果核对独立于负责人权限，旧任务也不能借重放绕过版本检查。

上传原件时，可先暂存文件；最终挂接、替换或删除客户材料时必须复验授权及版本。已转交的旧上传任务不能继续修改客户材料，未使用的暂存文件按清理策略处理。

## 5. AI、翻译、邮件及系统任务

### 5.1 纯读取能力

具备相应读取及 AI 功能权限的员工，可以阅读和纯翻译其他员工负责客户的邮件。纯翻译可以异步执行并缓存译文、摘要；由于客户改派不改变全员可读规则，仅因改派不必取消纯翻译任务。

纯翻译不得顺带更新申请状态、写入补件、完成任务或发出邮件。缓存是派生读取结果，不得将其包装成业务状态变更。任务及结果访问仍须遵守成员状态、功能权限和另行配置的敏感字段权限。

### 5.2 业务动作

发信、更新申请、确认材料、写入补件及其他办理动作必须经过业务写授权；AI 判断或建议不能代替当前负责人的权限。带有业务副作用的 AI 工具调用、工作流及 MCP 命令也适用同一规则。

已有关联申请的邮件，应以服务端确认的申请所属客户作为业务归属，避免邮箱重新绑定后旧邮件随绑定变化而被错误授权。无法明确归属的邮件，在确认客户前不得由普通员工执行客户业务动作。

一般阅读摘要可以按读取能力提供；回复方向、AI 起草和重新起草属于办理辅助，须检查对应功能与客户权限。保存正式业务草稿、发送和修改业务记录分别授权。发送执行前还须复验 `ownerVersion`、草稿/邮件版本以及附件有效性。

### 5.3 系统任务

邮箱收取、同步、索引及纯翻译缓存等基础处理使用范围明确的服务身份，并记录来源。服务身份不是绕过所有业务权限的通用例外。

收信和纯翻译本身不直接推进申请状态。是否在首版接入独立的自动业务解析/推进策略由 Q-03 决定；启用前须单独定义授权主体、允许动作、客户范围、改派行为和审计规则，不能直接继承后台写 key 的全部能力。

## 6. 待确认规则

以下是技术提案，尚未被确认，不能写成已经决定或已经实现：

| 问题 | 建议方案 | 实施要求 |
| --- | --- | --- |
| 新建客户默认负责人 | 新建人默认负责；管理员可在创建时指定其他负责人 | 普通员工能否新建仍受创建功能权限控制；确认后再固定创建接口行为 |
| 未分配客户由谁办理 | 仅管理员可办理或分配 | 不得把负责人为空解释为任何员工可写；普通员工读取仍按已确认规则 |
| 普通员工创建新客户时如何赋值 owner | 后端按经验证的创建者赋值，不接受任意 owner | 此提案是创建动作的特例，不开放普通员工后续修改 owner |

在上述规则确认前，相关创建/未分配流程不得以宽松的授权回退进入上线验收。

## 7. 验收标准

使用合成客户 X、Y；员工 A 负责 X，员工 B 负责 Y；管理员 M 具备所需管理及业务功能权限。另准备缺少某项功能权限的用户，验证“负责人权限”和“功能权限”同时生效。

| 场景 | 预期结果 |
| --- | --- |
| A、B 使用原生列表、详情、搜索、获准 API/MCP 读取 X、Y | 均可读取功能权限允许的内容，不因不是负责人而隐藏客户 |
| A 经业务表单修改/办理 X，B 经业务表单修改/办理 Y | 成功，并记录真实发起人 |
| A 经业务接口修改/办理 Y，B 经业务接口修改/办理 X | 服务端拒绝；不能仅靠按钮隐藏 |
| A 直接用自己的 Twenty 会话/API/MCP 修改 X 或 Y | 原生业务写均拒绝，即使 X 由 A 负责 |
| 员工调用原生新增、删除、恢复、批量修改、导入或关联修改 | 不能绕过受控业务写入口 |
| M 经管理功能处理 X、Y并将 X 从 A 改派给 B | 成功，ownerVersion 递增，改派及业务审计完整 |
| A 已打开 X 编辑页，M 改派后 A 再提交 | 拒绝旧版本操作，不覆盖 B 的新数据 |
| A 的发信任务已排队但尚未发出，随后 X 改派 | 执行前被阻止；不得自动改用 B 身份发出 |
| 改派与发信开始并发 | 按共同排他机制形成确定顺序，不出现检查后越权发送；外部结果不明不自动重发 |
| X 改派后，A 的纯翻译任务完成 | 可按读取权限返回缓存译文；无申请状态、补件或发信副作用 |
| A 是负责人但缺少发信/材料/AI等目标功能权限 | 对应操作拒绝，不能凭 owner 绕过功能权限 |
| 伪造 userId、isAdmin、ownerId、customerId、工作区或关联 ID | 不改变服务端解析的真实身份和客户归属 |
| 用合法请求重放、复用旧 ownerVersion 或幂等键 | 不重复副作用，不恢复旧负责人权限 |
| 子任务、材料、草稿、附件属于另一客户 | 按真实所属客户拒绝越权写入；批量请求逐项授权 |
| 一个 Person 同时关联 X、Y，A 尝试修改共享主档 | 按首版技术方案拒绝；管理员维护共享主档，A仅改客户范围资料 |
| 为员工配置/遗留 READ_WRITE 或 FULL share | 配置检查或验收发现并移除，不允许其绕过原生对象只读 |
| 浏览器、前端组件及员工 MCP 配置检查 | 不包含后台写 key或可取得该 key 的接口 |
| 成员停用、功能权限撤销后执行已排队任务 | 执行前复验并拒绝需要该身份或权限的动作 |
| 未分配客户、新建默认 owner | 在规则确认后补齐对应测试；不得默认为已经通过 |

权限、转交并发、邮件执行前复验及幂等需有服务端测试；再用 A/B/M 做原生界面、自定义表单、REST、GraphQL 和 MCP 的集成/端到端验收。单次 MCP 初始化成功、读取成功或文档完成均不代表上述功能已实现。
